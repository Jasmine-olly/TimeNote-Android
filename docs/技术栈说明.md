# TimeNote 技术栈说明

> 面向非开发者的通俗解释
> 日期：2026-08-03
> 配套文档：[PRD](../PRD.md)

---

## 1. 什么叫「技术栈」

技术栈 = 建这个 App 用的「**语言 + 工具组合**」，就像盖房子的「建材清单」：

- 钢筋水泥 → 核心语言
- 按图纸搭框架 → UI 框架
- 装门窗 → 权限
- 接水电 → 后台任务

**TimeNote 的三个「反常规」需求**，直接决定了选型：

1. 要能**悬浮在其他 App 上面**显示计时（悬在抖音/游戏上面）
2. 要能**知道你现在正在用哪个 App**（检测前台应用）
3. 要能在别人 App 的**上方弹出提问弹窗**

这三件事在 Android 上都属于「**深度系统能力**」——只有原生的 Android 语言才能拿到这些钥匙。

---

## 2. 为什么选「原生 Kotlin」而不是 Flutter / React Native

这是最核心的一个决策。市面上流行的跨平台框架（Flutter、React Native）能一套代码同时出安卓版和苹果版，像写一次中文、翻译成两种方言。

但代价是：**它们是一层「翻译器」，够不到底层的系统抽屉**。而 TimeNote 要做的三件事——悬浮窗、前台检测、全屏弹窗——恰好都在那个「底层抽屉」里。

| | 跨平台框架 | 原生 Kotlin |
|---|---|---|
| 比喻 | 请一个翻译：能沟通，但拿不到本地人的钥匙 | 你就是本地人，钥匙就在口袋里 |
| 系统级能力 | 弱，难以触及 | 原生直接可用 |
| 代码复用 | 一套代码多端 | 仅 Android 端 |
| 适用场景 | 普通「界面型」App | 「系统插件型」App |

**结论**：对 TimeNote 这种「专攻系统级功能」的 App，原生是唯一可靠的答案。**代价**是只做安卓（恰好是已确认的方向），代码无法顺便生成苹果版。

## 3. 技术栈每一层是干嘛的（对应到功能）

| 技术 | 通俗解释 | 服务哪个功能 |
|---|---|---|
| **Kotlin** | 写这个 App 的「母语」 | 所有逻辑 |
| **Jetpack Compose** | 搭界面的「乐高积木」，声明式写 UI | 悬浮计时器、弹窗、日记翻页界面 |
| **Room** | 手机里的「本地档案柜」，可靠地存数据 | 存娱乐清单、问题计划、所有回答和日记 |
| **WorkManager / AlarmManager** | 系统级的「闹钟 + 定时器」 | 到点弹提问、每天自动汇编日记 |
| **UsageStatsManager** | 系统授权的「门卫监控」：告诉你前台是哪个 App | 检测正在用娱乐 App → 启动悬浮计时 |
| **AccessibilityService** | 备用「门卫」，实时性更强 | 兜底前台检测（因为上一个有延迟） |
| **SYSTEM_ALERT_WINDOW** | 系统的「悬浮窗许可证」 | 让你在游戏/视频上面看到计时和弹窗 |

---

## 4. 一句话总结

> 因为 TimeNote 要靠「悬浮在其他 App 上面 + 检测你在用什么 App」吃饭，所以必须用能直达 Android 系统底层的**原生 Kotlin**。Flutter 这类框架适合「普通界面型」App，不适合「系统插件型」App。

---

## 5. 快速对照：一个「普通 App」的技术栈长什么样

作为对比，如果 TimeNote 只是个普通记账 App，技术栈可能完全不同：

| | 普通记账 App | TimeNote |
|---|---|---|
| 框架 | Flutter / React Native（或原生） | 原生 Kotlin |
| 系统权限 | 基本不需要 | 悬浮窗 + 使用情况访问 + 无障碍（兜底） |
| 后台任务 | 简单 | 定时提问 + 每日汇编 + 持续前台检测 |
| 复杂度 | 中 | 高（系统级） |

这也说明：**需求越「系统化」，技术栈越要贴近系统底层**。

### 6.2 构建时需设置的环境变量
```
JAVA_HOME=<JDK 安装路径>
ANDROID_HOME=<Android SDK 路径>
```
> 注意：不设置 `JAVA_HOME` 时系统只会找到 JRE 8，无法满足 Gradle 9 的 JDK 17 要求。
> 本项目使用 **Gradle Wrapper**（`gradlew`），首次构建会自动下载对应 Gradle 版本到 `~\.gradle\wrapper\dists`。
